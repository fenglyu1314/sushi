## Why

M1 的核心循环（采购→生产→售卖→作废→结算）已在模拟层跑通，但目前只能靠 `m1_harness.gd` 用**写死的脚本化计划**做 headless 验证——它证明了机制正确，却无法回答路线图对 M1 的关键判断：**"玩家会想再玩一天，能感受到预测成功/失败的反馈"**。这个"好不好玩"的判断只能靠玩家**亲自交互决策**才能得出。因此需要一层白盒 UI，让人真正玩这条经济闭环。

同时，现有内容（食材/配方/顾客/地点）内联硬编码在测试脚本里，违背"数据驱动、加内容不改代码"原则；本变更一并落实把内容迁移为 `.tres` 数据资源，并提供在 Godot 编辑器中创建这些资源的分步指导。

## What Changes

- 新增**内容加载**：约定 `.tres` 数据资源目录，运行时加载食材/配方/顾客/地点为内容集，替代 `m1_harness.gd` 的内联硬编码内容。
- 新增**游戏会话编排**：一个主控脚本把 `DayCycle`、各系统（采购/生产/售卖/结算）、`RunState` 与内容集串成可玩的一天循环，并向 UI 暴露玩家动作（采购、生产、开摊、进入下一天）。
- 新增**决策阶段 UI**：采购与生产面板——展示现金/库存/可做份数，选择采购数量与生产份数，预览成本，点击"开摊"进入模拟。
- 新增**模拟阶段 UI**：按 tick 可视化推进，滚动展示成交/流失反馈、成品余量与实时营收。
- 新增**结算复盘 UI**：呈现营收/采购/租金/浪费/净利与各款售出、作废、流失明细，引导玩家复盘并进入下一天。
- 全程白盒占位：纯色矩形/圆形 + 文字标签，遵循固定网格与"占位可读性"（`AGENT.md` §4.4）。
- `.tres` 资源与场景（`.tscn`）由用户在 Godot 编辑器内按分步指导创建；AI 只落地脚本逻辑（`AGENT.md` §3.1/§3.5）。

## Capabilities

### New Capabilities
- `content-loading`: 从约定的 `.tres` 数据目录加载食材/配方/顾客/地点为运行时内容集，供会话与售卖等系统使用；加内容不改代码。
- `game-session`: 会话编排层，串联日周期、各系统与运行状态，向 UI 暴露玩家动作与当前可玩状态（现金、库存、成品、可做份数等）。
- `decision-ui`: 决策阶段的采购/生产交互面板，含成本预览与"开摊"入口。
- `simulation-ui`: 模拟阶段的 tick 推进可视化与成交/流失/营收实时反馈。
- `settlement-ui`: 结算复盘面板，呈现当日盈亏结构与各款成交/作废/流失明细，并进入下一天。

## Impact

- **新增脚本（AI 落地）**：`game/scripts/systems/content_db.gd`（内容加载）、`game/scripts/core/game_session.gd`（会话编排）、`game/scripts/ui/` 下决策/模拟/结算面板控制脚本。
- **用户在编辑器内操作**：创建 `.tres` 内容资源（食材/配方/顾客/地点，占位数值同 M1 content-manifest）；搭建白盒 UI 场景与节点树、连接信号、必要的 Autoload/主场景切换（AI 提供分步指导）。
- **依赖复用**：`DayCycle`（决策/模拟/结算阶段与 tick）、`EventBus`（成交/流失/作废/结算信号）、M1 各纯逻辑系统与数据模型，均不改动其需求。
- **收摊复盘**：吸收 `BACKLOG.md` 中"加强收摊后复盘表现"的想法（开销/收益/各款销量），纳入 `settlement-ui`；"流言"属后续里程碑内容，本变更仅预留展示位、不实现。
- **Non-goals（明确不做）**：正式美术；空间约束（冰箱/货架占格）；前排取货位/排队/犹豫窗口等临场操作；热度/情报/流言/随机事件；食材保质期；存档 UI（沿用既有 `SaveManager`，不新增界面）；GUT 自动化测试（M2 起引入）。
- **待定数值**：沿用 M1 的占位数值，均以数据资源承载，不硬编码。
