## Why

路线图把 **M1 街头摆摊核心循环**列为整个项目最关键的判断点：若"预测→采购→生产→止损"这个循环用白盒都不好玩，就要先调设计而非继续堆功能（见 `docs/03-开发路线图.md`）。M0 已完成时间/事件/存档地基，现在需要先把这条经济闭环做成**不依赖节点树的纯模拟层逻辑**，以便用命令行快速验证正确性，为随后的白盒 UI 手感验证打底。

本 change 只做**数据层 + 模拟层核心闭环**；白盒 UI、空间约束、临场排队等留给后续 change（见 §Impact 的 Non-goals）。

## What Changes

- 新增**数据资源模型**：食材、配方、顾客类型、地点四类数据结构，以及食材→寿司的份数转化模型（GDD §5.3、技术架构 §2），落实"加内容不改代码"的数据驱动原则。
- 新增**采购与库存**逻辑：开摊前用现金采购主料/辅料进库存；遵循摆摊阶段"开摊后不可补料"（GDD §5.1）。
- 新增**生产**逻辑：按配方消耗库存生产寿司，受辅料数值上限约束（辅料容器先简化为数值上限，暂不做冰箱/货架格子 pack）。
- 新增**售卖与需求**逻辑：按顾客喜好标签生成需求并判定是否成交，成交收钱、未满足记为流失（GDD §5.4/§5.6/§7.1）。
- 新增**日结算**逻辑：收摊时未售寿司作废（实亏＝食材沉没成本，非额外罚款），计算当日营收/成本/浪费/净利，产出可复盘的结算数据（GDD §5.6/§9.1）。
- 与 M0 衔接：采购发生在决策阶段、售卖在模拟阶段、作废与盈亏在结算阶段，复用 `day-cycle` 阶段推进与 `event-bus` 信号。

## Capabilities

### New Capabilities
- `game-data-model`: 食材/配方/顾客类型/地点的数据资源结构契约，以及食材→寿司份数转化模型。
- `procurement`: 开摊前采购食材、扣现金、入库存；开摊后库存只减不增。
- `sushi-production`: 按配方消耗库存生产寿司，受辅料上限/产能约束，自动计算可做份数。
- `sales`: 顾客到达、按喜好标签判定是否购买、成交结账与流失（机会成本）判定。
- `day-settlement`: 收摊结算——未售寿司作废（实亏沉没成本）、当日盈亏核算、复盘数据产出。

## Impact

- **新增代码**：`game/scripts/systems/` 下采购/生产/售卖/结算的纯逻辑脚本；数据资源类定义脚本（`Ingredient`/`Recipe`/`CustomerType`/`Location`）。均为纯 GDScript，尽量不依赖节点树，便于命令行/后续测试。
- **数据资源**：`.tres` 内容资源需由用户在 Godot 编辑器内创建（遵循 `AGENT.md` §3.1）；本 change 只提供数据结构定义与内容清单。
- **依赖**：复用 M0 的 `day-cycle`（决策/模拟/结算阶段）与 `event-bus`（信号解耦）；结算数据结构应可纯数据化，便于接入 `save-system`。
- **Non-goals（明确不做，留后续 change）**：白盒 UI 交互层；冰箱/货架格子 pack 空间约束（§5.2）；前排取货位 + 等待队列 + 犹豫窗口等临场操作（§5.5）；热度/情报/流言/随机事件（§7.5-7.7）；食材保质期（§9.1 摆摊阶段食材不过期）；GUT 自动化测试（技术架构 §9，M2 起引入）。
- **待定数值**：GDD §5.8/§7.8 标注的数值均为待调项，实现时用可配置的数据资源承载、不硬编码占位假数。
