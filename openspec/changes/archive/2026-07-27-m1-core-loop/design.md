## Context

M0 已交付时间/事件/存档地基（`day-cycle`/`event-bus`/`save-system`）。M1 要在其上实现摆摊阶段的核心经济闭环。GDD §5 的摆摊规则已确认，具体数值待原型调优（§5.8）。本 change 聚焦**模拟层纯逻辑 + 数据资源模型**，是"分两步验证 M1"策略的第一步：先用命令行验证闭环正确性，随后的独立 change 再叠加白盒 UI 验证手感。

约束：GDScript + Godot Resource（已确认）；模拟层尽量不依赖节点树以便测试；`.tres` 资源由用户在编辑器创建（`AGENT.md` §3.1）；数值不硬编码。

## Goals / Non-Goals

**Goals:**
- 用数据资源承载食材/配方/顾客/地点，落实"加内容不改代码"。
- 实现"采购→生产→售卖→作废→日结算"的纯逻辑闭环，与 `day-cycle` 三阶段对接。
- 闭环状态可纯数据化，便于命令行驱动验证，并为接入 `save-system` 留口。
- 通过 `event-bus` 广播关键事件（成交/流失/作废/结算完成），保持系统解耦。

**Non-Goals:**
- 白盒 UI / 任何表现层（下一个 change）。
- 冰箱/货架格子 pack 空间约束（§5.2）、前排取货位 + 等待队列 + 犹豫窗口（§5.5）。
- 热度/情报/流言/随机事件（§7.5-7.7）、食材保质期（§9.1 摆摊阶段不过期）。
- 数值平衡与"好不好玩"的主观评判（依赖后续白盒 UI）。
- GUT 自动化测试（技术架构 §9，M2 起引入）。

## Decisions

- **模拟层用 `RefCounted`/纯 class，不用 `Node`**：核心逻辑（采购/生产/售卖/结算）实现为不挂在场景树上的普通对象，仅通过 `event-bus` 对外广播。理由：技术架构 §4 要求模拟层与节点树解耦、便于测试；命令行验证时无需实例化场景。
- **单一 `RunState` 聚合当天可变状态**：现金、食材库存、辅料余量、成品寿司列表、当日统计（营收/成本/流失/浪费）集中于一个纯数据对象。理由：便于整体存档、便于结算一次性汇总；替代方案（状态散落各 system）不利于存档与复盘。
- **数据资源用 `Resource` 子类脚本 + `@export` 字段**：`Ingredient`/`Recipe`/`CustomerType`/`Location` 各定义一个 `extends Resource` 脚本，实例数据存 `.tres`。理由：编辑器可视化编辑、GDScript 原生支持、无缝数据驱动。份数由"原料总量 ÷ 配方每份消耗量"自动算出（§5.3），一种食材支持多配方，扩展不改份数表。
- **需求生成基于顾客喜好标签（§7.1）**：顾客以 `{标签:权重}` 建模；地点决定顾客构成与人流量。M1 先用"顾客想要某款具体寿司"的确定性需求（§5.4 教学友好），售卖判定＝货架上有无该款。理由：先跑通"预测-止损"主张力，情报/概率化留给后续。
- **与 `day-cycle` 对接的阶段职责**：决策阶段＝采购 + 生产（开摊前即时完成，§5.1）；模拟阶段＝按 tick 推进顾客到达与售卖；结算阶段＝未售寿司作废 + 当日盈亏核算 + 产出复盘数据。理由：直接复用 M0 阶段机，不新造时间模型。
- **两类"亏"显式区分（§5.6）**：流失只计机会成本、不扣钱、食材留库存（摆摊阶段可跨天，§9.1）；作废是实亏，亏的是食材采购沉没成本、倒掉动作本身不额外罚款。理由：这是核心 Hook，必须在数据结构与结算公式上落到实处。

## Risks / Trade-offs

- **无 UI 难判"好不好玩"** → 本 change 只承诺验证机制正确性；主观手感验证明确交给下一个白盒 UI change，避免范围蔓延。
- **数值全待定，跑出来的结果无参考** → 数值以可配置数据资源承载并给占位初值（标注为占位），先验证机制连通，不追求平衡。
- **需求模型过简，预测张力不足** → 先用确定性需求打通闭环，为喜好标签/情报保留接口；若验证发现张力不够，在设计层回调而非在本 change 强行加码。
- **`.tres` 需用户手动在编辑器创建，易与脚本字段脱节** → 本 change 交付清晰的资源类定义 + 内容清单，字段变更时同步更新清单并提示用户。
