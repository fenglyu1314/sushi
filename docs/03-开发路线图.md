# 开发路线图

> 原则：白盒优先，先验证"好不好玩"，再做正式美术。每个里程碑都要有明确的**可验证目标**。

---

## 原型优先级（先难点验证，后扩展）

```
M0 项目骨架 ─▶ M1 摆摊核心循环 ─▶ M2 传送带 ─▶ M3 座位/服务员 ─▶ M4 多厨房 ─▶ M5 布局优化
   (地基)       (验证是否好玩!)     (核心中期)    (自动化)         (广度)      (高玩长线)
```

**关键判断点在 M1**：如果"预测-采购-生产-止损"这个核心循环用白盒都不好玩，就要先调设计，而不是继续往下堆功能。

---

## 里程碑

### M0 — 项目骨架
- Godot 4.7.1 工程、Git 仓库、目录结构、事件总线、时间/tick 系统、基础存档。
- **验证**：能运行一个空的"一天"循环（决策→模拟→结算）。

### M1 — 街头摆摊核心循环（最关键）
- 食材/配方/顾客数据资源；采购、生产、售卖、卖不掉作废、日结算。
- 单一地点、几种寿司、简单喜好。
- **验证**：玩家会"想再玩一天"，能感受到预测成功/失败的反馈。

### M2 — 小店 + 回转传送带
- 传送带容量与占位逻辑；食材保质期/过期；随机事件（涨价/降价/忌口）。
- **验证**：空间约束 + 保质期 + 事件让决策明显更有深度。

### M3 — 扩张：自动化 + 独立座位
- 厨师(自动生产)、独立座位(点单制)、服务员(送餐产能)。
- **验证**：玩家能体会"浪费流(传送带) vs 精准流(点单)"的权衡。

### M4 — 多品类厨房
- 拉面/烧烤等新产线接入同一循环与数据框架。
- **验证**：新增品类不需大改架构（数据驱动是否成立的检验）。

### M5 — 布局优化玩法
- 网格放置、寻路（服务员/顾客）、吞吐效率计算与反馈。
- **验证**：不同摆法产生可感知的效率差异，形成"优化"乐趣。

---

## 美术替换策略

- 全程白盒占位，正式像素美术在玩法稳定后，**按系统逐步替换**（食材图标 → 寿司 → 顾客 → 场景）。
- 白盒与正式资源共用相同网格尺寸与命名，降低替换成本。

## 与 OpenSpec 的配合

- 每个里程碑内的具体功能，用 OpenSpec 走「propose → apply → archive」流程。
- 本路线图是宏观计划；细粒度需求/规格在各自的 change 中沉淀。
